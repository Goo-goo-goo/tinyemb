# 性能压测 — Intel Celeron J3160(NAS 真机)

在低功耗 NAS(J3160)上的真实压测记录。所有环境变量使用默认值,内存占用约 240MB。

## 硬件

| 项 | 值 |
|---|---|
| CPU | Intel Celeron J3160(Braswell 架构,2016) |
| 核心 | 4 核 @ 1.6-2.24GHz(低功耗,6W TDP) |
| 指令集 | **SSE4.2**(不支持 AVX/AVX2) |
| 部署 | Docker,全变体模式自动选 `sse42` 内核 |
| 内存占用 | **~240MB**(Q8_0 量化 + 运行时) |

## 压测结果

### 1. 单条延迟(不同文本长度)

| 文本 | token | p50(ms) | p99(ms) |
|---|---|---|---|
| 短(2字) | 4 | 55 | 57 |
| 中(7字) | 9 | 104 | 112 |
| 长(~80字) | 94 | 847 | 858 |
| 超长(~240字) | 242 | 2255 | 2342 |

> 延迟随 token 数快速增长(注意力 seq²),J3160 算得慢,超长文本 2 秒+。

### 2. 并发吞吐(单条 input)

| 并发 | 吞吐(req/s) | p50(ms) | p99(ms) |
|---|---|---|---|
| 1 | 9.7 | 105 | 109 |
| 2 | 16.4 | 110 | 187 |
| 4 | 19.7 | 192 | 304 |
| 8 | 21.4 | 373 | 541 |
| **16** | **22.3** | 695 | 912 |
| 32 | 21.9 | 1398 | 1834 |

> 吞吐在并发 8~16 饱和(~22 req/s),再加并发只堆延迟——**J3160 4 核算力瓶颈**。

### 3. 批量吞吐(input 数组)

| batch | 吞吐(句/s) | 每批延迟(ms) |
|---|---|---|
| 1 | 10.0 | 100 |
| 4 | 12.0 | 332 |
| 8 | 12.5 | 640 |
| 16 | 23.2 | 691 |
| 32 | 22.6 | 1418 |

> 批量收益有限(23 句/s),J3160 核太少,批量摊薄效果不明显。

## 结论

- **吞吐峰值:~22 req/s**(并发 8~16)
- **批量吞吐:~23 句/s**
- **内存:~240MB**(Q8_0,非常省,NAS 友好)
- **瓶颈:CPU 算力**(J3160 是 6W 低功耗 4 核,不是软件问题)

对 J3160 这类低功耗 CPU,22 req/s 是合理水平。适合**低并发、个人/小团队 NAS 场景**(如本地 RAG、语义搜索)。高吞吐需求需更强 CPU。

## 对比参考

| 平台 | 吞吐峰值 | 内存 |
|---|---|---|
| **Intel J3160(本报告)** | 22 req/s | 240MB |
| Intel Xeon Gold 5218(见 BENCHMARK-XEON-5218.md) | 30 req/s | — |
| Apple M3(开发参考) | 630 req/s | — |

> 注:跨平台差异主要来自 CPU 单核性能 + 核心数。J3160(4 低功耗核)→ Xeon(4 虚拟核)→ M3(4 性能核),算力递增。
> 端到端延迟含网络往返,纯推理延迟更低。

## 压测方法

```bash
# NAS 上运行(服务已在 127.0.0.1:8000)
python3 scripts/bench.py           # 完整压测
python3 scripts/bench.py --quick   # 快速压测
```

脚本自动:健康检查、预热、多并发、批量,输出格式化结果表。
