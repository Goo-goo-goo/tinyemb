# 性能压测报告 — Intel Xeon Gold 5218

对部署在服务器上的 tinyemb 服务做的压测记录。所有环境变量使用**默认值**。

## 测试环境

| 项 | 值 |
|---|---|
| CPU | Intel(R) Xeon(R) Gold 5218 CPU @ 2.30GHz |
| 架构 | x86_64 |
| 核心 | 4 核(Socket × Core = 4,单线程/核) |
| 虚拟化 | VMware(完全虚拟化) |
| 缓存 | L1d 32K / L1i 32K / L2 1024K / L3 22528K |
| 指令集 | SSE4.2, AVX, AVX2, **AVX-512**(F/DQ/BW/VL/CD) |
| 服务地址 | <server-ip>:8000 |
| 模型 | bge-small-zh-v1.5 |
| 配置 | 默认(`max_batch=8`, `workers=2`, `threads=2`) |

## 测试结果

### 1. 单条延迟(随文本长度)

| 文本 | token 数 | p50 (ms) | p99 (ms) |
|---|---|---|---|
| 2 字(「你好」) | 4 | 92.3 | 101.8 |
| 7 字(「北京的天气不错」) | 9 | 100.1 | 112.5 |
| ~40 字 | 46 | 141.0 | 149.5 |
| ~160 字 | 147 | 253.4 | 520.2 |

> 延迟包含 HTTP 往返 + 服务内部排队。短文本约 100ms,随 token 数增长(注意力 seq²)。

### 2. 批量请求吞吐(input 传数组)

| batch 大小 | 吞吐(句/s) | 每批延迟(ms) |
|---|---|---|
| 1 | 9.0 | 110.8 |
| 4 | 16.8 | 237.4 |
| 8 | 20.5 | 390.0 |
| 16 | 24.6 | 649.4 |

### 3. 并发压测(单条 input,多线程)

| 并发 | 请求数 | 吞吐(req/s) | p50(ms) | p99(ms) | max(ms) |
|---|---|---|---|---|---|
| 1 | 32 | 7.8 | 118.2 | 343.2 | 343.2 |
| 2 | 32 | 16.0 | 118.5 | 185.9 | 185.9 |
| 4 | 32 | 25.6 | 136.9 | 280.5 | 280.5 |
| 8 | 64 | **30.4** | 231.8 | 455.4 | 455.4 |
| 16 | 128 | 29.4 | 539.8 | 1050.2 | 1120.1 |
| 32 | 256 | 23.3 | 730.3 | 4933.5 | 6346.4 |

---

## 结论

- **吞吐峰值**:并发 8 时约 **30 req/s**;批量 input 16 时约 **25 句/s**
- **单条延迟**:短文本约 **100ms**(含 HTTP 往返),长文本(~160字)约 250ms
- **并发拐点**:并发 > 8 后吞吐不再上升(受限于 `workers=2` + 4 虚核),延迟快速上升

## 优化建议(默认配置下有提升空间)

当前用默认参数,针对该 4 核 Xeon 服务器可调整:

| 环境变量 | 默认 | 建议 | 预期 |
|---|---|---|---|
| `TINYEMB_QUANT` | `0` | `1` | 降内存(89→55MB),小 CPU 提速 |
| `TINYEMB_WORKERS` | `2` | `4` | 提高并发吞吐 |
| `TINYEMB_THREADS` | `2` | `2~4` | 按核数微调 |
| `TINYEMB_BATCH` | `8` | `8` | 已是峰值区间 |

```bash
# 优化配置示例
docker run -d -p 8000:8000 \
  -e TINYEMB_QUANT=1 -e TINYEMB_WORKERS=4 -e TINYEMB_THREADS=2 \
  -v $(pwd)/models:/app/models tinyemb
```

## 附:压测方法

- 客户端:Python `urllib` + `ThreadPoolExecutor`(从局域网内另一台机器发起)
- 每组并发先预热 3 次,再测正式请求
- 延迟为客户端观测的端到端时间(含网络往返 ~33ms)
- 服务端配置为 Docker 默认环境变量

> **注意**:客户端与服务器跨网络(约 33ms 往返),端到端延迟包含网络开销;
> 纯服务端推理延迟更低(单条约 70-100ms,见 PERFORMANCE.md)。
